# RootLens 面试问题与口述答案

> 本文把 EchoMind 作者面经中的高频问题按主题合并，再按 RootLens 当前代码和验收记录重写答案。原题号用于回查面经；答案只描述 RootLens 已实现或已验证的内容，计划中的能力会明确标注。

## 怎么使用

不要背整篇。先看[中文架构图与请求流程](33-rootlens-architecture-walkthrough-cn.md)，把模块和具体例子连起来，再用第 1 题的项目介绍和第 4 题的请求链路打底，按面试官追问的方向展开。每个答案先说结论，再解释一个具体例子，最后说明当前边界。

题目来自作者的项目面经与《echo如何拿去面试》。同一问题在原材料里往往有多个版本，这里合并成一题；括号中的原题号方便回到原文。答案按 RootLens 的现状重写，不代表原作者的项目回答。

## 一、项目与业务

### 1. 你做的项目是什么？（原面经：项目介绍、目标）

RootLens 是给企业技术支持和运维团队使用的服务异常研判工作台。客户或内部同事报告服务报错后，系统先按服务和时间查询日志、指标、发布记录，再结合故障 Runbook 分析。应用、数据库和基础设施 Agent 可以从不同领域一起判断，最后输出现场查到的事实、还需要验证的原因和建议动作。

它还保存每次诊断的过程和历史，方便支持人员解释“为什么这么判断”。目前现场数据是版本化模拟数据，系统还没有接入企业真实日志、监控或发布平台。

### 2. 谁会用它？它解决什么实际问题？（原面经：系统主要目标、运维场景）

一线技术支持、实施交付、运维或 SRE 收到故障反馈时，通常要在日志、监控、发布记录和内部手册之间来回查，再把信息交给研发团队。RootLens 把这些步骤放到一个诊断流程里，先整理证据，再形成可追溯的判断和交接内容。

它的定位是辅助研判和沟通，不是自动修复生产故障。现在提供的是可运行的诊断链和模拟数据，不会真的执行生产回滚或操作客户系统。

### 3. 为什么不把问题直接发给大模型？（原面经：运维排查为何需要 Agent 架构）

只把一句“服务 5xx 了”发给大模型，它没有当前服务的日志、指标和发布信息，只能凭常识猜。RootLens 先用受控工具查询这些现场数据，再把带来源的结果交给模型分析。这样模型的结论至少能对照具体记录，证据不足时也可以明确要求补充信息。

这里的大模型负责理解和分析，查询范围、数据来源、路由和输出格式由程序约束。当前工具连的是模拟故障数据，所以这证明的是诊断链可工作，不代表已经具备真实生产取证能力。

### 4. 从用户输入到最终结果，完整链路是什么？（原面经：完整请求链路）

用户提交问题后，系统先读取当前会话上下文并识别意图和 RootLens 实体。若属于需要现场调查的故障类型，就根据服务、环境和事件时间建立查询范围，调用日志、指标和发布记录工具。工具返回的结果整理成 Evidence，再用其中有来源的错误信息增强 Runbook 检索。

之后编排器结合用户意图和 Evidence 产生领域分数，选择主 Agent 和辅助 Agent。Agent 结果交给结构化诊断组装器，Pydantic 校验输出和证据引用；系统同时记录 Trace，最后尝试把诊断与 Trace 保存为历史记录并返回前端。

如果只是问 Runbook，或缺少服务名、时间等必要信息，就不会盲目扫描全部数据，而是走知识查询或澄清路径。

### 5. 项目有哪些主要模块？（原面经：项目模块划分）

我通常按一次诊断来介绍：IntentRecognizer 负责理解问题，Evidence 工具负责查现场，KnowledgeBase 负责查 Runbook，AgentOrchestrator 负责选主辅 Agent，DiagnosisAssembler 负责生成并校验结构化结果，Trace 负责记录执行过程，Evaluator 负责按固定案例检查行为，Repository 负责保存历史，React 控制台负责交互和查看。

这样讲比只报目录名更容易理解：每个模块都对应诊断链上的一个步骤。

## 二、Agent 与路由

### 6. 为什么拆多个 Agent，不让一个通用 Agent 处理？（原面经：多 Agent 的作用、为什么不用一个 Agent）

应用故障、数据库故障和基础设施故障关注的信号不同。比如 5xx 和发布关系更偏应用，连接池耗尽更偏数据库，CPU 或节点异常更偏基础设施。把领域职责分开后，路由结果和各领域的分析重点更清楚。

但 Agent 数量不是越多越好。当前是一个通用运维分诊 Agent 加三个领域 Agent；它们共享同一个模型客户端，现场工具由诊断流程集中调用。多 Agent 的收益是职责分工和协同分析，不是每个 Agent 都有独立模型或一套自主工具循环。

### 7. 现在有哪些 Agent？分别负责什么？（原面经：Agent 角色和边界）

- `GeneralOpsAgent`：通用运维分诊、证据不足时的信息说明，以及部分专业 Agent 失败后的兜底；角色 Prompt 也包含澄清和跨领域总结要求。
- `ApplicationAgent`：应用错误、5xx、接口超时和发布相关问题。
- `DatabaseAgent`：连接池、慢查询、锁等待和数据库连接异常。
- `InfrastructureAgent`：CPU、内存、磁盘、网络、节点和网关问题。

例如 payment-service 出现 5xx，同时日志里有 `DBConnectionError`，应用 Agent 通常作为主 Agent，数据库 Agent 作为辅助 Agent。主辅是本次分工，并非某个角色永远只能做辅助。Agent 人工升级只是诊断状态和建议，目前没有接入真实工单或人工值班平台。

要区分角色描述与实际调用：缺服务或时间时，Pipeline 通常直接用规则返回澄清，不必调用 GeneralOps 模型；统一结构化结果由 DiagnosisAssembler 组织，也不是每次都再调用 GeneralOps 总结。结合[架构导读的 M06、M07 与图 3](33-rootlens-architecture-walkthrough-cn.md)看会更清楚。

### 8. 多 Agent 是怎么协作的？它们会互相对话吗？（原面经：主辅 Agent、并行执行）

当前是主 Agent 和辅助 Agent 并行分析同一份用户描述、现场证据和知识上下文，各自使用对应角色 Prompt 和匹配 Skills。编排器用 asyncio.gather 并发等待，每个 Agent 返回自己的分析与执行状态；成功回复按主辅顺序拼接，同时把执行记录和本次真实资料交给 DiagnosisAssembler 组织并校验统一结构化诊断。

它们不会互相发消息，也没有先让一个 Agent 完成、再把中间结果交给另一个 Agent 的串行工作流。面试时可以准确称为“主辅 Agent 并行协作”，不要说成自主多 Agent 对话。

### 9. 只识别一个 Intent，为什么还能触发多个 Agent？（原面经：单主意图与多 Agent、关键词路由争议）

Intent 表示用户这次最主要想调查什么；主辅 Agent 路由则判断还需要哪些领域一起看。比如用户主要描述“发布后 5xx”，主 Intent 可以是 `deployment_issue`，但现场日志出现 `DBConnectionError` 后，Evidence 会给数据库领域一个路由信号，于是数据库 Agent 可以作为辅助角色。

Intent 不会被 Evidence 改写，用户实体也不会被工具结果覆盖。证据只额外提供路由信号，帮助识别跨领域问题。这样能保持 Intent 契约简单，同时不漏掉次要但重要的故障领域。

### 10. 意图模糊时为什么不把请求交给所有 Agent？（原面经：低置信度下多 Agent 是否合理）

如果什么都不清楚就让所有 Agent 一起猜，成本和延迟都会上升，还可能给出互相矛盾的建议。RootLens 会先检查是否缺少服务、时间等必要信息；诊断条件不足时先澄清，不做全库扫描，也不为了凑答案臆测非 demo 日期。

多 Agent 用于有多个清楚领域信号的情况，不用于替代必要信息收集。

### 11. Evidence 怎么影响 Agent 路由？（原面经：Agent 路由和领域信号）

系统先按 Intent、用户描述和实体生成原始领域分数，再从 operational Evidence 中提取领域信号。例如 5xx 可以支持应用领域，`DBConnectionError` 或连接池耗尽可以支持数据库领域，CPU 或节点异常可以支持基础设施领域。信号通过分数下限合并，不会因为重复日志条数多就无限加分。

这个分数是路由用的启发式分数，不是统计意义上的根因概率。Runbook 和历史事故只提供知识，不参与现场领域打分。

## 三、意图与实体

### 12. 意图识别目前怎么做？（原面经：三路融合识别器）

RootLens 保留了共享的意图识别器，但兼容模型配置下当前主要使用 LLM 和 Pattern 两路，按 85% 和 15% 合并。向量意图路径在配置支持时可用；当前兼容接口环境没有启用它，所以不能把 RootLens 当前路径说成正在使用三路融合或真实语义 Embedding。

识别结果包含主 Intent、置信信息和实体等结构化字段，供后续澄清和路由使用。权重是当前实现配置，不是通过大规模实验训练出来的最优参数。

### 13. Intent 和 Agent 有什么区别？（原面经：意图分类与 Agent 分类）

Intent 描述用户想做什么，例如调查服务故障、排查发布问题或查询 Runbook；Agent 描述由哪个专业角色处理。多个 Intent 可以映射到同一个 Agent，一个 Intent 也可能根据证据需要多个 Agent 协作。

比如 `deployment_issue` 是请求的主要调查方向，ApplicationAgent 负责主分析，而日志中的数据库错误可能再让 DatabaseAgent 参与。

### 14. 实体怎么抽取？怎么避免旧客服实体污染？（原面经：IntentResult、实体提取）

RootLens 在共享识别器输出后做显式实体投影，只允许当前业务认可的字段进入 RootLens 路径：`date`、`service_name`、`start_time`、`version`、`status_code` 和 `error_code`。空列表、空值和空字符串会被过滤，订单号、金额、商品等旧客服字段不会进入 RootLens Request、Agent 上下文或接口输出。

共享识别器仍保留旧字段兼容，因此这个过滤发生在 RootLens 业务边界，不是把旧能力从整个项目里删掉。

### 15. 什么情况下会追问？（原面经：模糊意图和澄清）

需要运行态取证但缺少服务名，或者使用 demo 数据时无法确定事件日期，系统会要求补齐必要信息。它不会擅自把当前电脑日期当成故障日期，也不会扫完整个数据集碰运气。

用户补充后，前端会带上原问题、补充内容和事件时间重新提交诊断。历史记录的“解读已有诊断”和“重新取证”是两种不同操作，前者不会把旧结论冒充成当前现场事实。

## 四、Evidence 与工具

### 16. 三个故障查询工具具体做什么？（原面经：工具接入、现场排查）

当前有 `query_logs`、`query_metrics` 和 `query_deployments`。它们按服务、环境和时间窗口过滤版本化模拟数据，返回带稳定 ID、时间和来源的 Evidence。日志和指标查看故障前后窗口，发布记录则额外向前查找，以免漏掉故障前刚发生的发布。

三个工具由 DiagnosisPipeline 统一触发，不是让 Agent 随意生成工具名后直接访问真实平台。当前 provider 是模拟 JSON 数据，替换成真实日志或监控系统时，需要实现对应数据适配器并继续保持查询边界和 Evidence 契约。

### 17. 为什么使用模拟故障数据？这在项目里站得住吗？（原面经：真实故障案例和工具效果）

真实客户日志和监控通常涉及权限、脱敏和平台接口，当前项目没有这些授权。因此第一版使用版本化模拟数据，确保同一案例里的日志、指标、发布记录相互一致，并能重复运行和测试。

它适合证明查询契约、证据来源、路由、结构化输出和降级链路；不能证明线上实时诊断能力，也不能声称提升了真实故障解决率。下一步要增强真实性，应接入有授权的测试环境数据，而不是把模拟数据说成生产数据。

### 18. `ok`、`empty`、`failed`、`degraded` 分别是什么？（原面经：工具异常和降级）

`ok` 是查询成功且有记录；`empty` 是查询成功但没有匹配记录；`failed` 是工具调用本身失败；`degraded` 表示部分结果或降级路径仍可用。它们不能互相替代。

例如某服务在时间窗内没有发布记录，正确状态可能是 `empty`，不能写成工具故障。反过来，日志服务超时也不能伪装成“现场没有错误”。明确区分这些状态，Agent 才不会把系统故障当成业务事实。

### 19. 为什么把日志、指标、发布记录并行查询？（原面经：一次请求链路）

这三类查询依赖相同的服务和时间条件，但互相之间不需要等待。系统用 `asyncio.gather` 并发等待它们，缩短 I/O 查询总等待时间。它不会让 CPU 密集计算自动变快。

每个工具仍有自己的超时和状态，所以其中一个失败时，系统可以保留其他成功证据，而不是把整组查询全部算失败。

### 20. 怎么避免把“刚发布”误判成根因？（原面经：证据与结论可靠性）

发布时间靠近故障只能说明时间相关，不能证明因果。RootLens 把发布记录作为一条 operational Evidence，Agent 可以把它列为需要调查的线索，但结构化诊断要把已经观察到的事实和待验证假设分开。

例如可以说“异常发生在 v2.3.7 发布后，建议对比连接池配置和版本变更”，不能仅凭时间顺序写“v2.3.7 导致故障”。

## 五、RAG 与 Skills

### 21. RAG 在 RootLens 里解决什么问题？（原面经：知识库构建与检索）

现场工具回答“这次故障查到了什么”，Runbook RAG 回答“遇到这类现象通常按什么步骤排查”。RootLens 使用独立的 `rootlens_runbooks_v1` collection，存放连接池耗尽、应用 5xx、发布排查等 Runbook 和历史事故材料，避免加载退款、发票等客服知识。

Runbook 是通用知识，不是本次故障的现场证据，也不会直接给某个 Agent 的领域分数加分。

### 22. RootLens 的 RAG 检索链路是什么？（原面经：Query Rewrite、Multi-query、Rerank）

检索先从用户原问题开始，把有 operational Evidence ID 支持的错误词作为可选补充；随后尝试查询改写和多路召回，把不同子查询结果按稳定 chunk ID 合并去重，再用 LLM 对候选做重排，取 Top-K Runbook 给 Agent 使用。

改写、召回、重排各自记录真实状态。改写失败时可以退回原始问题；重排失败时保留原排序，但不能把失败记录成已成功执行。项目当前仍有额外 Runbook 命中噪声，没有证明某个设置让真实检索准确率提升了多少。

### 23. BM25、向量检索和 Rerank 分别是什么？RootLens 用了哪些？（原面经：混合检索）

BM25 按关键词匹配找候选；向量检索按文本向量的相似度找候选；Rerank 对已经召回的候选再排序。RootLens 当前使用 ChromaDB 向量检索、查询改写、多路召回、去重和 LLM Rerank，没有实现 BM25 混合召回。

Rerank 只能重新排列候选，不能找回前面完全没有召回的文档。之后是否加 BM25，应通过固定案例比较关键词错误码查询的召回变化和整体成本来决定。

### 24. Rerank 用的是什么模型？为什么不用专用 Cross-Encoder？（原面经：LLM Rank、模型类型）

当前 Rerank 调用的是配置的大语言模型接口，不是 Embedding 模型，也不是本地 Cross-Encoder。它读取原问题和候选片段，按相关性返回排序结果，再由程序校验索引并取 Top-K。

这样做是为了复用已有模型接口，先完成检索链路；这不代表 LLM Rerank 的效果优于 Cross-Encoder。专用 Cross-Encoder 可能更适合低延迟、大批量精排，应该在有固定评测集后比较质量、延迟和成本再决定。

### 25. 查询改写为什么有用？它有什么风险？（原面经：Rewrite 必要性）

用户可能说“服务忽然报错”，Runbook 里写的是“HTTP 5xx”或“连接池耗尽”。改写可以从不同角度生成检索词，增加找到相关文档的机会；保留原始问题则能降低改写跑偏的影响。

它会增加模型调用和延迟，也可能引入不相关表达。RootLens 对没有 Evidence 支持的根因猜测不做 query 增强，改写失败时退回原问题。是否改善召回仍应通过标注了目标 Runbook 的案例做 Recall@K 等评测，不能凭主观感受下结论。

### 26. Skills 和知识库有什么区别？（原面经：Skill 是 SOP 还是知识检索）

Runbook RAG 提供“这种故障的处理知识”；Skill 提供“某个 Agent 按什么规范分析和表达”。例如连接池 Runbook 讲检查连接数、超时和配置的步骤；Database Skill 会提醒 Agent 区分事实和假设，不要把缺失证据写成确认结论。

RootLens 的 Skill 按 Agent 类型和关键词匹配后注入上下文，支持热加载。它不是独立状态机，也没有自动执行 Skill 文件中的脚本。

### 27. Skills 的结构和触发方式是什么？（原面经：Skill 文件结构与加载）

每份 Skill 有名称、描述、适用 Agent、关键词、启用状态和正文。SkillManager 按 Agent 白名单和关键词筛选，再把符合条件的规则放到 Agent 的提示上下文中。`/skills/reload` 可以重新加载规则。

关键词匹配简单、可解释，但同义表达覆盖有限。当前还没有语义向量 Skills 检索；以后可以用评测 bad case 决定是否增加语义匹配，而不是先把所有 Skills 都塞给模型。

## 六、Memory、结构化输出与 Trace

### 28. RootLens 的记忆系统有哪些部分？（原面经：三层记忆）

RootLens 默认保留 Redis 当前会话记忆，保存最近消息和摘要。代码还支持 ChromaDB episodic 和 user_profile，但 RootLens 默认关闭用户画像读取和更新，也不自动召回其他会话的 episodic 内容，避免客服用户画像或历史会话污染一次故障诊断。

所以面试时不能照搬“三级记忆都在 RootLens 正常参与回答”的说法。当前会话 Redis 是运行中的能力，跨会话长期记忆默认隔离。

### 29. 对话太长导致上下文窗口不够怎么办？（原面经：上下文窗口和摘要）

当前会话消息超过阈值时，系统会让模型生成摘要，再压缩较早消息并保留最近对话。摘要失败或内容无效时不会先删旧消息，避免信息丢失。Redis 工作记忆使用会话级 TTL。

RootLens 默认不把其他会话的历史摘要自动塞进故障诊断。当前实现控制了消息保留和摘要，但还不是按 token 精确分配每一类上下文预算的方案。

### 30. 为什么需要结构化诊断？Pydantic 能解决什么？（原面经：最终回复和结果格式）

自然语言 Markdown 方便人读，但前端、历史查询和评测难以稳定地抽取字段。`IncidentDiagnosis` 把状态、服务、确认事实、待验证假设、建议、证据引用和工具状态固定成 schema；Pydantic 检查字段类型与枚举，运行范围校验再检查引用 ID、真实状态和已定义风险规则。

校验失败时保留可读回复并明确标记结构化结果失败，不把半合法 JSON 当成成功。Pydantic 能检查格式和引用是否存在，不能保证每句话在语义上都被证据支持，所以仍需要证据来源审查和回归案例。

### 31. Diagnosis 和 Trace 有什么不同？（原面经：监控与调用轨迹）

Diagnosis 记录“最后得出了什么”：事实、假设和建议。Trace 记录“诊断过程中每一步怎么样”：Intent、工具、RAG、路由、Agent 和组装阶段是否成功、耗时多少、引用了哪些来源。

当前 Trace 覆盖诊断核心链，已经随 DiagnosisRun 保存到 SQLite，并可通过历史 Trace API 查询。它不是完整 HTTP 分布式追踪，也没有接入 OpenTelemetry 后端。

### 32. 故障注入做了什么？（原面经：失败降级和可靠性）

故障注入只用于测试，通过受控 Test Double 模拟工具超时、RAG 失败、辅助 Agent 失败、主 Agent 降级和结构化组装失败等情况。它检查系统是否保留仍可用的信息、是否把失败状态记录正确、是否拒绝不合法结构化结果。

注入机制不通过普通 `/chat` 参数开放，所以普通用户不能随意让线上请求失败。测试覆盖说明这些路径在受控条件下可复现，不代表已经验证真实供应商宕机或生产高并发。

## 七、评测与历史

### 33. 怎么评估系统效果？（原面经：评测链路、回答质量）

RootLens 的 `/eval/run` 复用 `/chat` 使用的核心诊断入口。Evaluator 先只把用户输入、环境和事件时间交给诊断链；整条链运行完成后才读取 expected，对照 Intent、主辅 Agent、Evidence、工具状态、澄清结果和 Runbook ID 计算确定性指标。

自然语言质量可以再用 LLM Judge 辅助评价，但 Judge 无效或 JSON 解析失败会单独标记，不能伪造一个默认分数。这样可以区分系统回答问题和评测器自身失败。

### 34. 如何防止评测答案泄漏？（原面经：参考答案与 Judge）

评测数据分 runtime 和 expected 两部分。runtime 中是实际查询用的日志、指标、发布记录；expected 中是正确 Intent、路由、Evidence、Runbook 和禁止结论。诊断运行结束后 Evaluator 才读取 expected 进行比较。

如果标准答案进入工具、RAG 或 Agent Prompt，测试就等于把答案提前给系统，结果不能说明系统独立完成了诊断。项目用确定性测试检查这条数据边界。

### 35. 评测集有多大？6/6 能说明什么？（原面经：测试集规模和指标可信度）

目前 RootLens 正式评测套件是六个合成案例，覆盖典型故障、Runbook 查询、澄清和部分证据情形。Stage 5 收口时的真实模型评测中，结构化诊断 6/6 构建成功、Judge v2 6/6 有效；离线回归记录也覆盖更多单元和故障路径。

六个案例只能说明固定小型回归集通过，不能说生产准确率 100%，也不能推出真实用户场景的总体表现。扩充到真实规模前，需要有授权、脱敏、人工标注并覆盖不同故障分布的数据。

### 36. LLM-as-Judge 评什么？它可靠吗？（原面经：Judge 维度和人工抽检）

Judge 评四项：证据依据、诊断推理、建议可执行性、安全与不确定性表达。它根据 diagnosis、runbook 或 clarification 模式采用对应 rubric；输出必须通过 schema 校验，失败样本不进入有效均值。

Judge 是辅助评估，不是绝对真值。当前 Judge v2 只在六案例上验证过，尚未进行大规模人工校准，所以重要结论仍需结合确定性指标、人工抽查和具体案例判断。

### 37. Baseline 是什么？如何避免把回归比较错？（原面经：评测基线）

Baseline 是经过人工批准的一份历史评测结果，用来和后续同版本评测比较。RootLens 会记录 suite、数据集、schema、模型/provider、案例 ID 和 fingerprint；版本不兼容时不应该直接算 regression。

Baseline 只适用于对应的合成套件，不是生产质量认证。Promote 需要显式人工决定，旧版本结果作为历史快照保留。

### 38. 一次诊断如何保存？为什么还需要 DiagnosisRun？（原面经：结果与执行记录）

`IncidentDiagnosis` 是结构化结论，`DiagnosisTrace` 是执行过程，`DiagnosisRun` 把它们与原始请求和时间信息关联成一次诊断记录。SQLite 通过 Repository 保存和查询历史，评测请求不会写进普通用户诊断历史。

保存失败会标记持久化状态，但不会把已经生成的诊断回答一起丢掉。当前 SQLite 适合本地演示和单机验证，还没有验证多实例高并发写入。

## 八、工程取舍与项目复盘

### 39. 你觉得开发中最难的是什么？（原面经：项目难点）

最难的是让模型结论和来源对得上。模型能把一段话写得很顺，但如果把空日志误写成“日志发现连接错误”，听起来合理也仍然是错的。

我们遇到过部分证据场景里，模型把一个来源的 Evidence ID 配到了另一个说法上。后来修正模拟记录的来源边界，增加结构化引用校验、回归测试和人工来源审查。这个经历让我意识到，格式正确和 ID 存在不等于结论真实，必须核对每个结论具体由哪条证据支持。

### 40. 遇到“问 A 答 B”怎么排查？（原面经：bad case 排查、错误回答）

我会按执行链逐层看：Intent 和实体是否正确；Evidence Gate 是否应该查现场；工具的服务、环境和时间范围是否正确；拿到的是空结果还是调用失败；Runbook 有没有命中目标文档；路由和 Skill 是否合适；最后检查 Agent 输出、结构化校验和历史上下文。

RootLens 的 Trace、tool status、Evidence ID 和 Runbook ID 能帮助定位具体步骤。修复时先把 bad case 固定成回归用例，再改对应模块，避免只改提示词却没查清数据或路由问题。

### 41. 为什么不用 LangGraph、CrewAI 或 n8n？（原面经：是否使用编排框架）

当前诊断链路是固定顺序：先取证、再检索知识、再路由、再生成诊断。现有 Orchestrator 和 Pipeline 足以表达这套流程，直接引入新框架会增加状态适配和回归成本。

如果以后出现长时间运行、可暂停恢复、复杂分支和跨系统工作流，再评估 LangGraph 或外部流程平台。现在没有因为面试关键词而加框架。

### 42. 为什么用 Redis、ChromaDB 和 SQLite？（原面经：存储策略）

它们对应不同访问方式：Redis 保存当前会话短期状态；ChromaDB 做 Runbook 向量检索；SQLite 保存结构化诊断历史和分页查询。现在项目规模和部署方式适合这样分工。

这不表示生产环境一定要用这三种。若出现多实例并发写入、复杂迁移和多人协作需求，历史库可以升级 PostgreSQL；向量库也要按规模和运维能力重新评估。

### 43. 当前项目有哪些真实验证？还缺什么？（原面经：项目效果和指标）

当前有固定合成案例的真实模型评测、结构化诊断和 Judge 校验、Stage 1 到 Stage 5 的离线回归、可控故障注入，以及 Docker 和前端验收记录。最近一次记录的后端测试为 322/322、前端为 22/22；六案例真实评测为结构化诊断 6/6、Judge 6/6 有效。

这些数字要带着范围讲：它们是当前代码、固定案例和受控环境的验收结果，不是生产故障准确率。还缺真实日志/监控平台接入、较大规模人工标注集、生产负载测试和 Judge 大规模校准。

### 44. 这个项目是从零做的吗？你的工作是什么？（原面经：是否使用已有架构）

RootLens 是在已有多 Agent 运行时基础上的二次开发。我没有把整套底层运行时说成从零原创；我负责把它改造成故障诊断场景，并逐步补上 RootLens 的 Intent/实体边界、模拟 Evidence 工具、独立 Runbook 知识库、证据影响路由、结构化诊断、评测对齐、Trace、故障测试、SQLite 历史和前端工作台。

开发过程中使用了 AI 编程工具协助阅读、实现和排查，但每一阶段都按源码、测试和真实验收记录确认结果。面试时应能指到具体改动和验证证据，不把工具生成的代码自动等同于个人理解。

### 45. 这个界面是不是只是一个聊天框？（原面经延伸：项目展示）

前端是一个诊断工作台。新请求可以补充服务、环境和事件时间；结果页把现场事实、假设、建议、证据和工具状态分开显示；历史页支持筛选、查看详情和 Trace。

从历史打开时，可以选择解释已有诊断或重新取证。前者解释归档结果，不重新查现场；后者创建新的诊断运行。这两个入口分开，避免把旧结论误当成本次故障事实。

## 十、面试前速记

### 项目一句话

> RootLens 帮技术支持和运维人员先查服务现场证据，再结合 Runbook 和专业 Agent 做异常研判，并把结论、依据和执行过程记录下来。

### 请求链路一句话

> 识别问题和实体，按条件查日志、指标、发布记录，用现场证据增强 Runbook 检索，再选主辅 Agent，校验结构化诊断，记录 Trace 并保存历史。

### 三个最重要的边界

1. 模拟现场数据，不是生产平台实时数据。
2. 主辅 Agent 并行协作，不是 Agent 自主多轮互聊。
3. 六案例回归通过不等于生产准确率达到 100%。

### 推荐学习顺序

先练第 1、2、4 题，让没听过项目的人听懂；再练第 6、9、16、21 题，讲清 Agent、路由、工具和 RAG；最后准备第 30、33、39、43、44 题，覆盖结构化输出、评测、难点、验证和个人贡献。
